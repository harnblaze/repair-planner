# CLAUDE.md

## 1. Назначение проекта

Это веб-приложение для планирования и управления работами ремонтно-строительного цеха.

Основная задача приложения — помочь мастеру:

* принимать и фиксировать заявки от других цехов;
* планировать выполнение заявок по рабочим дням;
* назначать исполнителей;
* учитывать фактически использованные материалы;
* контролировать остатки материалов;
* вести дополнительные рабочие списки;
* в будущем формировать отчёты по расходу материалов.

UX частично вдохновлён концепцией Tweek: календарное планирование задач по дням + дополнительные списки/колонки.

Tweek используется только как UX-референс. Не копировать его код, дизайн или закрытые решения.

# 3. Главный принцип

Не пытайся написать как можно больше кода.

Цель — создать:

* простой;
* надёжный;
* безопасный;
* расширяемый;
* понятный;
* поддерживаемый

продукт.

Не превращать MVP в ERP.

# 4. MVP

В MVP пользователь должен иметь возможность:

1. зарегистрироваться;
2. войти в приложение;
3. создать несколько проектов;
4. переключаться между проектами;
5. создать категории/цеха-заказчики;
6. создать исполнителей;
7. создать материалы;
8. создавать заявки/задачи;
9. помещать задачи в список текущих заявок;
10. планировать задачи на конкретные рабочие дни;
11. назначать исполнителей;
12. указывать фактически использованные материалы;
13. изменять статус задачи;
14. переносить незавершённую задачу на следующий рабочий день;
15. пропускать субботу и воскресенье при переносе;
16. видеть остатки материалов;
17. получать предупреждение о низком остатке;
18. использовать дополнительные рабочие списки.

---

# 5. Что НЕ входит в MVP

Не реализовывать без отдельного указания:

* сложную RBAC-систему;
* приглашения пользователей;
* совместное редактирование;
* Telegram;
* email-уведомления;
* push-уведомления;
* полноценный складской модуль;
* закупки;
* бухгалтерию;
* сложные финансовые отчёты;
* производственный календарь;
* отпуска;
* автоматическое распределение загрузки сотрудников;
* сложную аналитику;
* мобильное приложение;
* офлайн-режим.

При этом архитектура должна позволять добавить эти функции позже.

---

# 6. Проекты

Пользователь может иметь несколько проектов.

Примеры:

* Работа
* Личное
* Бизнес

Данные разных проектов должны быть изолированы.

В будущем пользователь сможет пригласить другого пользователя только в конкретный проект.

Поэтому архитектура должна заранее предусматривать:

project_members

с возможностью определить пользователя и его уровень доступа.

Полноценную систему приглашений в MVP не реализовывать.

---

# 7. Безопасность Supabase

Это одно из самых важных требований проекта.

Использовать Row Level Security (RLS).

Нельзя полагаться только на проверки frontend.

Каждая пользовательская сущность должна быть защищена на уровне PostgreSQL/Supabase.

Проверять доступ как минимум для:

* projects;
* project_members;
* tasks;
* categories;
* executors;
* materials;
* task_executors;
* task_materials;
* material_movements;
* board_lists;
* других пользовательских сущностей.

Пользователь A не должен иметь возможности:

* прочитать данные пользователя B;
* получить чужой проект;
* получить чужую задачу;
* изменить чужую задачу;
* изменить чужой материал;
* изменить чужой остаток;
* получить данные проекта, к которому у него нет доступа.

Особое внимание уделять IDOR и аналогичным проблемам.

---

# 8. Авторизация

Использовать Supabase Auth.

Минимально:

* регистрация;
* вход;
* выход;
* восстановление пароля;
* защищённые маршруты;
* профиль пользователя.

Все пользователи MVP имеют одну основную роль: мастер.

Не создавать сложную RBAC-систему без необходимости.

Но не проектировать систему так, чтобы последующее добавление ролей стало невозможным.

# 9. Архитектурные решения

Перед реализацией значимых частей необходимо понять существующую архитектуру проекта.

Не переписывать работающий код без причины.

Не создавать абстракции только ради абстракций.

Предпочитать:

* простую архитектуру;
* понятные зависимости;
* небольшие компоненты;
* явную бизнес-логику;
* переиспользуемые функции там, где это действительно нужно.

---

# 10. Next.js

Использовать App Router.

Предпочитать Server Components там, где Client Component не требуется.

Client Components использовать только там, где необходима интерактивность:

* drag-and-drop;
* формы;
* интерактивный календарь;
* модальные окна;
* локальное состояние;
* другие browser-only возможности.

Не делать весь проект `"use client"`.

---

# 11. Supabase

Для серверной работы использовать корректный SSR-подход для текущей версии Supabase и Next.js.

Не хранить service role key в браузере.

Никогда не отправлять секретные ключи клиенту.

Не отключать RLS ради удобства разработки.

Если для серверной операции необходима повышенная привилегия, сначала проверить, можно ли решить задачу через корректные RLS policies или PostgreSQL function.

---

# 12. База данных

Перед созданием таблиц обязательно разработать модель данных.

Основные предполагаемые сущности:

* profiles;
* projects;
* project_members;
* tasks;
* categories;
* executors;
* task_executors;
* materials;
* task_materials;
* material_movements;
* board_lists;
* board_items или подходящая альтернатива.

Этот список не является обязательным.

Если после анализа требуется другая модель — объяснить почему.

---

# 13. Supabase migrations

Изменения базы данных должны выполняться через migrations.

Не редактировать production database вручную, если это можно выразить migration.

Каждая migration должна быть:

* последовательной;
* воспроизводимой;
* понятной;
* идемпотентной там, где это уместно;
* безопасной.

Не удалять данные или колонки без явного понимания последствий.

Перед изменением существующей схемы сначала изучить все существующие migrations.

---

# 14. RLS

Для каждой новой пользовательской таблицы необходимо задать RLS.

При создании новой таблицы автоматически задавать вопрос:

> Кто должен иметь право SELECT / INSERT / UPDATE / DELETE?

Не создавать таблицу без продуманной политики доступа.

RLS должна учитывать не только `user_id`, но и membership проекта там, где это необходимо.

---

# 15. Проекты и доступ

Основной принцип:

User → Project → Project data

Если пользователь владеет проектом — он имеет полный доступ.

В будущем участник проекта сможет иметь ограниченный доступ.

Не делать проверки доступа исключительно по:

```text
task.user_id = auth.uid()
```

если задача принадлежит проекту.

Сначала определить, имеет ли пользователь доступ к проекту.

---

# 16. Задачи

Минимальные поля задачи:

* id;
* project_id;
* title;
* description;
* category_id;
* status;
* created_at;
* updated_at;
* completion date;
* planned date;
* position.

Дополнительные поля добавлять только при необходимости.

Задача может иметь:

* несколько исполнителей;
* несколько материалов.

Использовать many-to-many связи.

---

# 17. Статусы

Использовать:

* new;
* planned;
* in_progress;
* paused;
* completed;
* cancelled.

UI может отображать русские названия.

В базе использовать стабильные значения.

Не завязывать бизнес-логику на русские строки интерфейса.

---

# 18. Категории

Категория представляет цех-заказчик.

Примеры:

* Механический;
* Энергетический;
* Сварочный;
* Транспортный.

Категории принадлежат проекту.

Пользователь может:

* создавать;
* редактировать;
* архивировать/удалять

категории в пределах доступного проекта.

Если удаление категории может нарушить исторические данные, предпочесть archive/soft delete.

---

# 19. Исполнители

Исполнитель MVP — обычная запись справочника.

Например:

Иванов Иван — сварщик.

Исполнитель не является пользователем Supabase.

Поля:

* id;
* project_id;
* name;
* position;
* active;
* timestamps.

Задача может иметь нескольких исполнителей.

Исполнитель может быть назначен на несколько задач.

---

# 20. Материалы

Материал принадлежит проекту.

Минимальные поля:

* id;
* project_id;
* name;
* unit;
* current_balance;
* minimum_balance;
* active;
* timestamps.

Не создавать сущность warehouse/склад.

---

# 21. Расход материалов

В задаче пользователь указывает фактически потраченное количество.

Не хранить в MVP отдельное planned_quantity.

Например:

```text
Электрод — 2 кг
Диск — 3 шт
Краска — 1 л
```

Необходимо сохранить связь:

task ↔ material

и количество расхода.

---

# 22. История движения материалов

Не полагаться только на `current_balance`.

Архитектура должна предусматривать историю:

* receipt;
* consumption;
* adjustment.

Полноценный UI прихода и корректировок пока не требуется.

Расход должен быть связан с задачей.

Это необходимо для будущих месячных отчётов.

---

# 23. Материальные операции

Изменение остатка материала и запись расхода должны быть атомарными.

Нельзя допустить ситуацию:

расход записался, но остаток не изменился.

И наоборот.

При необходимости использовать PostgreSQL function / transaction.

Не пытаться эмулировать транзакцию последовательностью независимых frontend-запросов.

Учитывать race conditions.

---

# 24. Отрицательные остатки

Не придумывать бизнес-правило молча.

Перед реализацией определить:

* запрещать расход больше остатка;
* разрешать отрицательный остаток;
* или предупреждать пользователя.

Если это критично и не определено требованиями — задать вопрос.

---

# 25. Низкий остаток

Если:

```text
current_balance <= minimum_balance
```

показывать предупреждение внутри приложения.

Не добавлять в MVP email/Telegram/push.

---

# 26. Календарь

Основная доска проекта содержит рабочие дни.

MVP:

* понедельник;
* вторник;
* среда;
* четверг;
* пятница.

Суббота и воскресенье считаются выходными.

Логику определения следующего рабочего дня вынести в отдельную бизнес-функцию.

Не дублировать её по компонентам.

Будущая архитектура должна позволять добавить:

* праздники;
* производственный календарь;
* индивидуальные графики.

---

# 27. Перенос задач

Если задача должна продолжиться:

понедельник → вторник

четверг → пятница

пятница → понедельник.

Не создавать новую независимую задачу при обычном переносе.

Сохранять идентичность исходной задачи.

Если потребуется история переносов, создать отдельную сущность/историю.

Перед выбором модели для длительных задач проанализировать:

* простой planned_date;
* task_schedule;
* task_occurrences;
* history.

Выбрать решение, которое не создаёт архитектурного тупика.

---

# 28. Дополнительные списки

В проекте должны существовать дополнительные списки:

* Текущие заявки;
* Материалы к заказу;
* Напоминания;
* Мероприятия.

Не создавать четыре полностью независимые реализации.

Предпочтительно использовать универсальную модель списков.

В будущем пользователь должен иметь возможность создавать свои списки.

# 29. UX

Основная цель UI:

Приоритет:

1. понятность;
2. скорость работы;
3. минимум кликов;
4. визуальная иерархия;
5. адаптивность;
6. эстетика.

Не превращать приложение в перегруженный dashboard.

---

# 30. Формы

Использовать:

* React Hook Form;
* Zod.

Валидация должна происходить:

* на клиенте;
* на сервере.

Никогда не доверять данным только потому, что frontend их проверил.

---

# 31. Обработка ошибок

Пользователю показывать понятные сообщения.

Плохо:

```text
insert failed: duplicate key...
```

Хорошо:

```text
Не удалось сохранить задачу. Попробуйте ещё раз.
```

Технические детали должны попадать в логи, а не пользователю.

Не показывать:

* stack trace;
* secret keys;
* SQL;
* внутренние идентификаторы;
* чувствительную информацию.

---

# 32. Даты и timezone

Календарное планирование является критически важной частью приложения.

Не использовать даты без понимания timezone.

Определить timezone приложения явно.

Не полагаться на случайный timezone браузера.

Особое внимание:

* смене дня;
* смене недели;
* пятнице → понедельнику;
* сохранению planned date;
* отображению дат.

---

# 33. Производительность

Использовать:

* pagination там, где она действительно нужна;

# 37. Работа по этапам

Работать итеративно.

Перед большим изменением:

1. изучить существующий код;
2. определить зависимости;
3. определить затрагиваемые файлы;

5. проверить security implications.

# 39. Git

Не выполнять опасные Git-операции без явного разрешения.

Никогда самостоятельно не делать:

* git reset --hard;
* force push;
* удаление веток;
* переписывание истории.

Не удалять пользовательский код без необходимости.

Если предлагается commit — сначала показать краткое описание изменений.

---

# 40. Secrets

Никогда не записывать секреты непосредственно в исходный код.

Использовать environment variables.

Никогда не выводить пользователю содержимое:

* API keys;
* service role keys;
* access tokens;
* passwords;
* secrets.

---

# 41. Проверка перед завершением

Перед заявлением «готово» проверить:

* TypeScript;
* lint;
* tests;
* build, если это возможно;
* RLS;
* отсутствие очевидных security vulnerabilities;
* корректность миграций;
* отсутствие console errors;
* корректность основных пользовательских сценариев.

Если что-то не проверено — прямо сообщить об этом.

# 43. Главный принцип

Всегда предпочитай:

простое корректное решение

вместо:

сложного «идеального» решения.

Но простота не должна достигаться за счёт:

* безопасности;
* целостности данных;
* расширяемости;
* корректности бизнес-логики.

Если есть архитектурный выбор, который может повлиять на будущее проекта, сначала объясни варианты и выбранное решение.
