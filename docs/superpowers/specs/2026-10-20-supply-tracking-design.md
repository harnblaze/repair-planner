# Снабжение: заказ и поставка ТМЦ — дизайн

Дата: 2026-10-20. Статус: на согласовании.

## 1. Цель

Цех заказывает материалы (ТМЦ) через отдел снабжения и долго ждёт: сначала
счетов, потом поставки. Мастер должен **не забывать, что заказали, что
оплатили и что привезли**.

Процесс цеха:

1. Цех составляет заявку на ТМЦ (Excel, пример — `ТМЦоктябрь2026г.(кабмех).xls`,
   34 позиции: наименование, ед., кол-во, «особые требования»), подписывает и
   отправляет в ОМТС. Ждёт.
2. Снабжение присылает счета от разных поставщиков (примеры: ЦСК №89598 от
   08.10.2026 — 31 строка; Лемана ПРО №079 000-221702/2656 от 06.10.2026 —
   4 строки). Цех выбирает и оплачивает один или несколько счетов — у одного
   поставщика может не быть всего. Ждёт.
3. Материалы привозят с УПД (счёт-фактура + накладная). Один скан содержит
   несколько УПД с разными датами (ЦСК: №84009 от 16.10 — линолеум, №84089 от
   19.10 — гвозди). По ним цех принимает материалы.

Что видно в реальных документах и определяет модель:

- **Названия, единицы и количество в заявке и счёте различаются.**
  «Саморезы по дереву 35мм, шт, 1500» → в счёте две строки: «Саморез 3,8х35
  (1000шт), упак, 1» и «Саморез 3,8х35 (100шт), шт, 5». «Линолеум T93 3.5м,
  пог. м, 5,2» → «м², 18,2». Автоматически сравнивать количества нельзя.
- **Бывают замены.** Лемана: в заявке профиль «ПК 03-9… шампань», в счёте
  «ПК 02.2700.15 … чёрный».
- **Бывают позиции вне заявки.** УПД №84089: «Гвозди строительные 4,0х120
  (25кг)», 2 упак — в заявке их нет.
- **Поставка по счёту идёт частями** (несколько УПД по одному счёту).
- В самой заявке нет номера и даты (только «в октябре 2026 г.») — их вводит
  мастер.

## 2. Решения, принятые с пользователем (2026-10-20)

| Вопрос | Решение |
|---|---|
| Приёмка → остаток материала | **По кнопке.** У привезённой строки кнопка «Оприходовать»: мастер выбирает материал справочника и кол-во в его единицах → приход (`material_movements`, `receipt`). Автоматического прихода нет. |
| Сопоставление строк счёта с позициями заявки | **Вручную, построчно.** Строки счёта хранятся как в документе; к каждой мастер выбирает позицию заявки (приложение предлагает похожую). Одной позиции — сколько угодно строк; строка может быть «вне заявки». |
| Частичная поставка | **Да, с количеством.** Строку счёта можно привезти несколькими поставками (УПД: номер, дата). |
| Неоплачиваемые (отклонённые) счета | **Не хранятся.** Вносятся только счета, которые цех оплачивает; статус «не оплачен» / «оплачен (дата)». |
| Счёт и заявки | **Счёт относится к одной заявке.** |
| Прикрепление файлов (xls, pdf) | **Позже, вместе с ИИ.** Модель оставляет место (§9), идея — в roadmap. |
| Ввод позиций и строк счёта | **Вставка из Excel** пачкой с предпросмотром + добавление по одной. |
| Позиция, которую так и не закажут | **Отметка «снята»**: позиция серая, зачёркнутая, не мешает заявке стать «привезена целиком». |

## 3. Решения исполнителя (можно поменять при чтении)

1. **Название раздела — «Снабжение»**, сущность — «заявка на ТМЦ». Слово
   «заявки» в приложении уже занято задачами от цехов («Текущие заявки»).
   Маршрут `/[projectId]/supply`, пункт в `components/common/project-nav.tsx`
   после «Материалы».
2. **Статусы не хранятся, а вычисляются** из строк счетов и поставок (§5) —
   нельзя получить «зелёную» позицию, которую на самом деле не привезли.
3. **Количество заявки и счёта не сравниваются** (единицы разные). Позиция
   считается заказанной, если к ней привязана хотя бы одна строка счёта; оба
   количества показаны рядом, мастер видит расхождение глазами.
4. **Перепоставка разрешена.** Привезли больше, чем в строке счёта — строка
   считается привезённой, показывается «привезено больше: 15 / 13».
5. **Оплата — целиком по счёту**, одной датой. Частичной оплаты нет.
6. **Сумма счёта — необязательное поле** (итог «Всего к оплате»). Цены по
   строкам не храним (roadmap).
7. **Оприходование нельзя отменить в этом этапе.** Ошибка исправляется
   пересчётом в «Материалах» (`set_material_balance`). Оприходованную строку
   поставки удалить нельзя (и, как следствие, её поставку, счёт, заявку).
   Отмена оприходования — в roadmap.
8. **Создание заявки/счёта/поставки вместе со строками — атомарно**, одной
   RPC `security invoker` (RLS применяется как обычно), а не двумя запросами
   с клиента (CLAUDE.md §23).
9. **Загружаются все заявки проекта** одним запросом с вложенными данными.
   Ожидаемый объём — десятки заявок в год по ~30 позиций. Поиск и фильтр —
   на клиенте. Пагинация/фильтр по году — в roadmap при росте.

## 4. Данные — миграция `0030_supply_tracking.sql`

Все таблицы — данные проекта: `project_id` (FK → `projects` on delete cascade),
у каждой `unique (id, project_id)` и составные FK `(…, project_id)` на
родителя, как в остальной схеме (docs/database.md §4). RLS для каждой таблицы:

| Операция | Кто |
|---|---|
| SELECT | `project_access(project_id) is not null` (владелец, редактор, просмотр) |
| INSERT / UPDATE / DELETE | `project_can_edit(project_id)` (владелец, редактор) |

`project_id` и ссылки на «родителя» неизменяемы: как в `task_queues` (0018),
`revoke update` на таблицу и `grant update (<изменяемые колонки>)`.
Триггер `set_updated_at` на всех таблицах. Числа — `numeric(14, 3)`, как у
материалов. Даты документов — `date` (без времени и timezone).

### 4.4 `supply_invoice_lines` — строка счёта «как в документе»

| Колонка | Тип | Примечание |
|---|---|---|
| id, project_id, created_at, updated_at | | стандарт |
| invoice_id | uuid not null | |
| request_id | uuid not null | денормализация ради целостности, неизменяема |
| request_item_id | uuid null | null — «вне заявки» |
| line_no | int not null | № строки в счёте |

Целостность декларативно, без триггеров:
- FK `(invoice_id, request_id)` → `supply_invoices (id, request_id)` on delete cascade;
- FK `(request_item_id, request_id)` → `supply_request_items (id, request_id)`

  другой заявки**; при удалении позиции строка становится «вне заявки»;
- FK `(request_id, project_id)` → `supply_requests (id, project_id)`.

`unique (id, invoice_id)` — цель для FK строк поставки. Индексы
`(invoice_id, line_no)`, `(request_item_id)`. UPDATE: `line_no, name, unit, quantity, request_item_id`.

### 4.6 `supply_delivery_lines` — сколько привезли по строке счёта

| Колонка | Тип | Примечание |
|---|---|---|
| id, project_id, created_at, updated_at | | стандарт |
| delivery_id | uuid not null | |
| invoice_id | uuid not null | неизменяема |
| invoice_line_id | uuid not null | |
| quantity | numeric(14,3) not null | > 0, в единицах строки счёта |

- FK `(delivery_id, invoice_id)` → `supply_deliveries (id, invoice_id)` on delete cascade;
- FK `(invoice_line_id, invoice_id)` → `supply_invoice_lines (id, invoice_id)`
  on delete cascade — **нельзя привезти строку чужого счёта**;
- FK `(invoice_id, project_id)` → `supply_invoices`;
- `unique (delivery_id, invoice_line_id)` — строка счёта один раз в одной поставке;
- `unique (id, project_id)` — цель FK из `material_movements`.

UPDATE: `quantity`.

### 4.7 `material_movements.supply_delivery_line_id` — «оприходовано»

```sql
alter table public.material_movements add column if not exists supply_delivery_line_id uuid;
-- FK (supply_delivery_line_id, project_id) → supply_delivery_lines (id, project_id) on delete no action
create unique index if not exists material_movements_supply_line_key
  on public.material_movements (supply_delivery_line_id) where supply_delivery_line_id is not null;
alter table public.material_movements add constraint material_movements_supply_receipt_check
  check (supply_delivery_line_id is null or kind = 'receipt');
```

`no action` (а не `restrict`): проверка в конце оператора. Удаление
поставки/счёта/заявки с оприходованной строкой падает (движение остаётся и
ссылается на неё) — приложение показывает понятное сообщение (§7). Удаление
**проекта** проходит: каскад удаляет и строки поставок, и движения в одном
операторе. Журнал движений остаётся неизменяемым.

### 4.8 RPC

Все — `set search_path = ''`, `revoke all … from public, anon`,
`grant execute … to authenticated`. Коды исключений — стабильные строки,
переводятся в `lib/errors.ts`.

1. **`create_supply_request(p_project_id, p_number, p_request_date, p_description, p_items jsonb) returns uuid`**
   — `security invoker`. Вставляет заявку и позиции (`[{line_no, name, unit, quantity, note}]`,
   может быть пустым) в одной транзакции. RLS проверяет права.
2. **`create_supply_invoice(p_request_id, p_number, p_invoice_date, p_supplier, p_amount, p_paid_on, p_lines jsonb) returns uuid`**
   — `security invoker`. Строки: `[{line_no, name, unit, quantity, request_item_id|null}]`.
   Чужая позиция отвергается FK (§4.4).
3. **`create_supply_delivery(p_invoice_id, p_number, p_delivery_date, p_lines jsonb) returns uuid`**
   — `security invoker`. Строки: `[{invoice_line_id, quantity}]`, минимум одна.
4. **`receive_supply_delivery_line(p_delivery_line_id, p_material_id, p_quantity, p_note) returns material_movements`**
   — `security definer` (вставка в `material_movements` без policy, как
   `record_material_movement`). Порядок:
   - найти строку поставки; нет или нет доступа (`project_access is null`) → `supply_line_not_found`;
   - нет права редактировать (`project_can_edit`) → `access_denied` (как в 0012);
   - материал не найден в **том же проекте** → `material_not_found`;
   - `p_quantity` null или ≤ 0 → `invalid_quantity`;
   - заблокировать строку поставки (`for update`); уже есть движение → `already_received`
     (гонка двух вызовов дополнительно закрыта уникальным индексом §4.7);
   - `repair_planner.balance_update = on`, `current_balance += p_quantity`,
     движение `receipt` с `supply_delivery_line_id`, `created_by = auth.uid()`,
     `note` = `p_note` или по умолчанию «УПД №… от ДД.ММ.ГГГГ, счёт №…».

Добавление позиций или строк счёта в существующую заявку/счёт — одна
вставка массива через PostgREST (один оператор — атомарно); `line_no`
продолжает нумерацию (max + 1…), совпадения номеров при гонке безвредны.
Отдельные UPDATE/DELETE (правка строки, «снять», отметка оплаты, удаление) —
обычными запросами через RLS, RPC не нужна.

## 5. Статусы (вычисляются, `lib/business/supply-status.ts`)

Чистые функции над загруженными данными, покрыты vitest.

**Строка счёта:** `delivered = Σ supply_delivery_lines.quantity`.
`none` (0) · `partial` (0 < delivered < quantity) · `full` (delivered ≥ quantity;
при `>` — флаг `over`).

**Позиция заявки** (первое подходящее):

| Статус | Условие | Вид |
|---|---|---|
| `cancelled` | `cancelled_at` задан | серая, зачёркнутая |
| `no_invoice` | нет привязанных строк счетов | жёлтая метка «нет счёта» |
| `delivered` | все привязанные строки `full` | **зелёная строка** |
| `partial` | хоть одна строка привезена (`partial`/`full`) | светло-зелёная, «частично» |
| `paid` | все счета привязанных строк оплачены | «оплачено» |
| `unpaid` | иначе | красная метка «не оплачено» |

**Заявка:** `delivered` («привезена целиком», зелёная шапка), если есть хотя бы
одна неснятая позиция и все неснятые — `delivered`; иначе `active`. Счётчики в
шапке: «в счетах N/M», «оплачено N/M», «привезено N/M» (M — неснятые позиции).
Строки «вне заявки» на статус заявки не влияют.

## 6. Интерфейс — `app/(app)/[projectId]/supply/`

Server Component `page.tsx` грузит заявки с вложенными позициями, счетами,
строками, поставками и признаком оприходования одним запросом. Интерактив —
Client Components: блоки заявок, диалоги, вставка. Формы — RHF + Zod; та же
Zod-схема на сервере в server actions (`actions.ts`). Роль «просмотр» видит
всё без кнопок изменения.

- Позиция с несколькими строками счёта — левая часть объединена (`rowSpan`).
- Сортировка заявок по `request_date desc`; позиции по `line_no`; строки счёта
  внутри позиции по дате счёта, затем `line_no`.
- «Активные» — заявки не в статусе `delivered`. Поиск — по номеру/описанию
  заявки, номеру/поставщику счёта, наименованиям позиций и строк счёта
  (без регистра, «ё» = «е»); найденная заявка разворачивается.
- По умолчанию развёрнуты активные заявки, свёрнуты привезённые. Состояние —
  в памяти страницы.
- Узкий экран: таблица прокручивается горизонтально внутри блока, страница —
  нет. Шапка блока переносится по строкам.

### 6.2 Действия

| Где | Действие |
|---|---|
| Шапка страницы | «+ Заявка на ТМЦ»: номер, дата (по умолчанию сегодня в timezone проекта), описание, необязательная вставка позиций. |
| ⋯ заявки | Изменить шапку, удалить (подтверждение; запрещено, если есть оприходованные строки). |
| «+ Позиции» | Вставка из Excel с предпросмотром или одна позиция. |
| Строка позиции (клик) | Диалог: правка полей, материал справочника (необязательно), «Снять» / «Вернуть», удалить. |
| «+ Счёт» | Номер, дата, поставщик, сумма, «уже оплачен» + дата; вставка строк счёта; предпросмотр с выбором позиции заявки для каждой строки. |
| ⋯ счёта | Изменить, «Оплачен…» (дата, по умолчанию сегодня) / «Снять оплату», добавить строки, удалить. |
| Строка счёта (клик) | Правка полей и привязки к позиции, удаление. |
| «+ Поставка» | Выбор счёта → № УПД, дата → список строк счёта с полем «привезено», по умолчанию = остаток (`quantity − delivered`, не меньше 0); строки с 0 не сохраняются. |
| Ячейка «Привезено» | Список поставок строки; у каждой — «Оприходовать» или «✓ оприходовано». Правка кол-ва и удаление строки поставки (если не оприходована). |
| «Оприходовать» | Диалог: материал справочника (подставлен `material_id` позиции, если задан; поиск по названию), кол-во в **единицах материала** (по умолчанию — привезённое, если ед. совпадает без учёта регистра и точки), примечание. Ссылка «Создать материал» — название и ед. из строки счёта. |

### 6.3 Вставка из Excel — `lib/business/supply-paste.ts`

- Вход — текст из буфера: строки через `\n`, ячейки через `\t` (Excel,
  LibreOffice, Google Таблицы).
- Колонки определяются по содержимому строки: число в первой ячейке при ≥ 4
  непустых — № п/п; кол-во — последняя ячейка, которая парсится как число
  (запятая или точка, пробелы-разделители тысяч); ед. — ячейка перед кол-вом,
  если она не число, иначе после него; наименование — самая длинная
  оставшаяся текстовая ячейка; остальной текст после кол-ва — примечание
  (для позиций заявки).
- Строки без наименования или без кол-ва > 0 — пропускаются и показываются в
  предпросмотре как «не распознано» (можно поправить вручную).
- Предпросмотр — редактируемая таблица (наименование, ед., кол-во,
  примечание / позиция заявки), удаление строк. Сохраняются только
  проверенные Zod строки.
- Текст из PDF (пробелы вместо табуляции) не разбирается гарантированно —
  подсказка в форме: «Скопируйте строки в Excel, затем сюда» (до ИИ, §9).

### 6.4 Подбор позиции к строке счёта — `lib/business/supply-match.ts`

Нормализация: нижний регистр, «ё»→«е», латинские двойники кириллицы
(T/Т, K/К, O/О, …) → один вид, знаки препинания → пробел, слова ≥ 2
символов и числа. Счёт: доля общих слов от слов позиции (Жаккар). Лучшая
позиция при счёте ≥ 0,35 предлагается в выпадающем списке предпросмотра,
мастер подтверждает или меняет; ниже порога — «вне заявки». Снятые позиции
не предлагаются. Одной позиции можно предложить несколько строк.

## 9. Будущее: ИИ-разбор документов (не в этом этапе)

Мастер загружает xls/pdf (заявка, счёт, УПД) → модель (например, DeepSeek)
извлекает шапку и строки → предпросмотр, тот же, что у вставки из Excel
(§6.3–6.4) → мастер подтверждает. Модель данных к этому готова:

- строки хранятся «как в документе» (наименование/ед./кол-во поставщика) —
  ИИ заполняет те же поля, что и вставка;
- создание с строками уже идёт через RPC с `jsonb` строк — ИИ-разбор
  вызывает те же функции;
- добавится таблица `supply_documents` (project_id, kind
  `request|invoice|delivery`, путь в Storage, статус разбора, сырой ответ
  модели) и nullable `document_id` у `supply_requests`, `supply_invoices`,
  `supply_deliveries`; текущие таблицы не перестраиваются;
- ключ API модели — только на сервере (server action / edge function),
  никогда в браузере.

## 10. Не входит в этап (→ docs/roadmap.md)

- Прикрепление файлов и ИИ-разбор (§9).
- Отмена оприходования (обратное движение `adjustment` и снятие связи).
- Цены и суммы по строкам счёта, отчёт по оплатам.
- Отклонённые/альтернативные счета.
- Пагинация или фильтр по году при сотнях заявок.
- Напоминания о долгой поставке («оплачено 30 дней назад, не привезено»).

## 11. Рассмотренные и отклонённые варианты

| Вариант | Почему нет |
|---|---|
| Хранимые статусы позиции/заявки | Расходятся с фактическими строками; вычисление дёшево при таком объёме. |
| Счёт целиком к заявке без построчной привязки | Не видно, какая позиция чем закрыта (выбор пользователя). |
| Строка счёта = позиция заявки (одна таблица) | Не выражает «одна позиция — несколько строк счёта», замены и «вне заявки». |
| Автоматический приход при отметке «привезено» | Единицы счёта и справочника различаются (упак vs шт); выбор пользователя — по кнопке. |
| Связь оприходования в колонке строки поставки | Пришлось бы менять строку при неизменяемом журнале; ссылка из `material_movements` + уникальный индекс проще и закрывает гонку. |
| Позиции заявки = `board_lists`/`board_items` | Нужны ед., кол-во, связи со счетами; универсальные списки обеднились бы. |
