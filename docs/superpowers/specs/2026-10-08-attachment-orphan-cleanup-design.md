# Очистка файлов-«сирот» в Storage — дизайн

Дата: 2026-10-08. Статус: на согласовании. Roadmap «После MVP», п. 10 (и п. 11 частично).

## 1. Проблема

В приватном bucket `task-attachments` могут оставаться файлы без строки
`task_attachments` («сироты»):

* **оборванная загрузка** — сервер выдал подписанную ссылку, браузер загрузил
  файл, но `confirmTaskAttachmentAction` не дошёл (закрыли вкладку, пропала
  сеть); самый частый случай;
* сбой удаления файла после удаления строки (`deleteTaskAttachmentAction`
  намеренно оставляет «сироту», а не битую миниатюру);
* сбой уборки после неудачной вставки строки при подтверждении.

Они невидимы для пользователя, но занимают место (бесплатный тариф Supabase —
1 ГБ Storage).

## 2. Решения, принятые с пользователем

| Вопрос | Решение |
|---|---|
| Как запускать | Автоматически после успешной загрузки фото в проекте, сессией пользователя. Без service role и планировщика. |
| Какие файлы | Старше суток, без строки `task_attachments` с тем же путём. Свежие не трогаются — это может быть загрузка в процессе. |
| Кто удаляет | Пользователь с правом редактирования проекта (owner, member) — по существующей RLS `storage.objects`. |

Отклонены (§8): кнопка в настройках, pg_cron + Edge Function с service role.

## 3. Ограничение платформы

Прямой `delete from storage.objects` запрещён триггером Supabase
`protect_objects_delete`, а файл в хранилище при этом остался бы. Удаление —
только через Storage API (`storage.from(bucket).remove(paths)`). SQL используется
лишь для поиска.

## 4. База данных — миграция 0026

`public.task_attachment_orphans(p_project_id uuid, p_limit int default 100) returns setof text`:

* объекты `storage.objects` с `bucket_id = 'task-attachments'`,
  `name like p_project_id::text || '/%'`, `created_at < now() - interval '1 day'`,
  для которых нет `public.task_attachments` с `storage_path = name`;
* только если `public.project_can_edit(p_project_id)`, иначе пусто — удалять
  файлы остальные всё равно не могут;
* порядок `created_at, name`; `limit least(greatest(coalesce(p_limit, 1), 1), 1000)`
  (у `remove` предел — 1000 путей за вызов);
* `language sql stable`, `set search_path = ''`, **security invoker**: RLS
  `storage.objects` (`task_attachments_objects_select`) и `task_attachments`
  действует;
* `revoke all … from public, anon; grant execute … to authenticated`.

Поиск идёт по индексу `storage.objects (bucket_id, name)`. Новых таблиц,
политик и индексов нет; выкладка безопасна в любом порядке относительно кода.

## 5. Код

* `lib/attachments/cleanup.ts` (серверный) —
  `cleanupAttachmentOrphans(supabase, projectId): Promise<number>`:
  RPC → если пути есть, один `remove(paths)`; возвращает число удалённых.
  Ошибки RPC и Storage — в `console.error`, функция не бросает.
* `confirmTaskAttachmentAction`: после успешной вставки строки (и при повторном
  подтверждении того же пути) — `after(() => cleanupAttachmentOrphans(supabase, projectId))`
  из `next/server`. Очистка выполняется после ответа и не замедляет загрузку;
  её сбой не влияет на результат действия.
* При неуспешном подтверждении очистка не запускается.

Размер пакета — до 100 файлов за загрузку: «сирот» мало, остаток уйдёт со
следующими загрузками.

## 6. Ошибки и безопасность

* Пользователь ничего не видит: ни успеха, ни ошибок очистки.
* Функция возвращает только пути (`{project}/{task}/{uuid}.jpg`), только по
  доступному для редактирования проекту; чужой проект — пусто (RLS + проверка).
* Удаление — сессией пользователя под RLS `task_attachments_objects_delete`:
  даже при ошибке в функции удалить чужие файлы нельзя.
* Гонка с загрузкой: файл загрузки в процессе моложе суток и не попадает в выборку.
  Гонка с подтверждением старого файла невозможна: подписанная ссылка
  действует 2 часа.

## 7. Тесты

pgTAP `attachment-orphans.test.sql` (фикстуры `storage.objects` вставляются
как postgres с нужным `created_at`):

* функция существует, `anon` без права выполнения;
* старый файл без строки — возвращается;
* свежий файл без строки, файл со строкой, файл чужого проекта, файл другого
  bucket — не возвращаются;
* viewer проекта — пусто; `p_limit` ограничивает выборку.

vitest `cleanup.test.ts`: удаляет найденное одним `remove`; пусто — `remove`
не вызывается; ошибка RPC или Storage — 0 и `console.error`, без исключения.
vitest `attachment-actions.test.ts`: успешное подтверждение планирует очистку
(`after`), неуспешное — нет.

Браузер (локально): «сирота» с `created_at` двухдневной давности в папке
задачи → загрузка фото в другую задачу проекта → «сирота» удалена, новое фото
на месте, консоль без ошибок.

## 8. Отклонённые варианты

* **Кнопка «Очистить» в настройках** — полный охват проекта, но ручной: мастер
  не будет её нажимать.
* **pg_cron + Edge Function с service role** — чистит независимо от
  активности, но новая инфраструктура вне миграций и секретный ключ на сервере;
  CLAUDE.md §11 требует сначала обойтись RLS.
* **Очистка SQL-триггером / pg_cron без Storage API** — невозможна (§3).

## 9. Вне этапа и связь с п. 11

* Проект, где фото больше не загружают, хранит «сирот» до следующей загрузки —
  это безвредно.
* П. 11 (удаление файлов при удалении задачи или проекта): каскадное удаление
  строк задачи превращает её файлы в «сирот», и эта очистка уберёт их через
  сутки при следующей загрузке в проекте. Удалённый проект так не очистится —
  при появлении удаления проектов файлы нужно удалять в том же действии.
  Roadmap п. 11 переформулируется соответственно.
