# Очереди и ручной порядок текущих заявок — дизайн

Дата: 2026-10-08. Статус: на согласовании.

## 1. Цель

1. **Ручной порядок.** Мастер перетаскивает заявки внутри панели «Текущие
   заявки» и расставляет их по приоритету. Порядок сохраняется после
   перезагрузки и одинаков для всех участников проекта.
2. **Очереди.** Кроме основной панели «Текущие заявки» мастер заводит свои
   очереди, например «Столярные дела»: столярных заявок много, их делает
   только столяр, и в общей куче они мешают. У каждой очереди своя панель
   на доске со своим ручным порядком.

Сейчас панель одна, её порядок нигде не хранится: запрос в
`app/(app)/[projectId]/board/page.tsx` сортирует по `created_at desc`.

## 2. Решения, принятые с пользователем

| Вопрос | Решение |
|---|---|
| Где хранить порядок | Колонка `tasks.backlog_position`. Отдельная таблица порядка и дробный ранг отклонены (§11). |
| Куда встаёт новая заявка | Наверх своей очереди. |
| Куда встаёт заявка, вернувшаяся с доски или с очищенной датой | Наверх своей очереди, независимо от места, куда её бросили. |
| Как заявка попадает в очередь | Мастер выбирает очередь явно: при создании (форма в панели очереди) или на странице заявки. Не по исполнителю и не по категории: категория — это цех-заказчик. |
| Очереди фиксированные или настраиваемые | Настраиваемые: добавить, переименовать, удалить в настройках проекта. «Текущие заявки» — основная очередь, её нельзя удалить или переименовать. |
| Модель очередей | Отдельная таблица `task_queues`; основная очередь — `tasks.queue_id is null` (вариант A). Очередь как разновидность `board_lists` отклонена (§11). |
| Чей порядок | Общий для проекта. |
| Кто меняет порядок, очереди и очередь заявки | Владелец и редактор (`project_can_edit`). «Только просмотр» — нет. |

## 3. Данные — миграция `0018_task_queues.sql`

### 3.1 `task_queues`

```sql
create table if not exists public.task_queues (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references public.projects (id) on delete cascade,
  name text not null check (char_length(btrim(name)) between 1 and 60),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (id, project_id)
);
create index if not exists task_queues_project_idx on public.task_queues (project_id, created_at);
```

- Основной очереди строки нет: это `queue_id is null`. Поэтому её нельзя
  удалить или переименовать по устройству модели, а существующие заявки
  переносить не нужно.
- Порядок панелей очередей на доске: основная, затем остальные по
  `created_at, id`. Ручного порядка панелей нет (§12).
- Имя не уникально: две очереди с одним именем не ломают данные, только
  путают мастера, а уникальность добавила бы ещё одну ошибку для перевода.
- `updated_at` — триггер `task_queues_set_updated_at` на общей функции
  `public.set_updated_at()`, как у `board_lists`.

**RLS** (включена):

| Действие | Кто |
|---|---|
| SELECT | любой участник проекта: `project_access(project_id) is not null` |
| INSERT / UPDATE / DELETE | `project_can_edit(project_id)` |

`project_id` у очереди неизменяем: UPDATE-политика с `with check` по тому же
проекту и триггер-страж не нужны, потому что составной FK заявок (§3.2) и
так не даст привязать заявку к очереди чужого проекта. Смену `project_id`
запрещаем правами на колонки: `revoke update on public.task_queues from
authenticated, anon; grant update (name) on public.task_queues to authenticated`.
Отозвать право только на `project_id` нельзя: Supabase выдаёт `authenticated`
право `update` на всю таблицу, и оно перекрывает отзыв на колонку.
`updated_at` ставит триггер, ему право на колонку не нужно.

### 3.2 `tasks`

```sql
alter table public.tasks add column if not exists queue_id uuid;
alter table public.tasks add column if not exists backlog_position int;

alter table public.tasks
  add constraint tasks_queue_fk
    foreign key (queue_id, project_id) references public.task_queues (id, project_id)
    on delete set null (queue_id);

create index if not exists tasks_queue_idx on public.tasks (queue_id) where queue_id is not null;
```

- Составной FK — тот же приём, что у `tasks.category_id` (docs/database.md
  §4): очередь чужого проекта отвергает сам PostgreSQL. При `queue_id is null`
  FK не проверяется.
- `on delete set null (queue_id)` (PostgreSQL 15+, у нас 17): при удалении
  очереди её заявки переходят в основную, `project_id` не трогается. Данные
  не теряются.
- `tasks_queue_idx` нужен для этого каскада: без индекса удаление очереди
  сканировало бы все заявки.
- Порядок панели очереди: `backlog_position asc nulls first, created_at desc, id`.
  Тот же порядок используют страница и RPC (§4), иначе после перестановки
  список «прыгнет». `null` — заявку ещё не расставляли: такие идут первыми,
  новые сверху.

### 3.3 Сброс позиции

Триггер `tasks_reset_backlog_position` — `before insert or update of
planned_date, status, queue_id on public.tasks`: `new.backlog_position := null`,
если это вставка, изменилась `planned_date` или `queue_id`, или статус
перешёл между открытыми и закрытыми (`completed`/`cancelled`).

Этого хватает на все пути входа в панель без правки существующих функций:

- новая заявка — `null`, наверх своей очереди;
- возврат с доски (`return_task_to_backlog`) — триггер пересчёта из 0008
  обнуляет `planned_date`;
- очистка даты на странице заявки (`set_task_planned_date`, 0015) — то же;
- планирование на день — позиция обнуляется; заявки в панели уже нет, а
  если вернётся — встанет наверх;
- переоткрытие завершённой или отменённой заявки без даты (статус меняется
  свободно на странице заявки) — наверх, а не на старое место;
- смена очереди на странице заявки и удаление очереди — наверх новой
  очереди.

Смена только `backlog_position` не трогает перечисленные колонки, поэтому
этот триггер и страж `tasks_guard_planned_date` на перестановку не
срабатывают.

## 4. RPC `public.move_backlog_task(p_task_id uuid, p_queue_id uuid, p_position int) returns void`

Одна функция и для перестановки внутри очереди, и для переноса в другую
очередь. `p_queue_id = null` — основная очередь. `language plpgsql`,
`security invoker`, `set search_path = ''`. Образец — `move_board_item` (0008).

1. Прочитать заявку (`project_id, status, planned_date, queue_id`). Нет
   строки (в том числе чужой проект — RLS её скрывает) → `task_not_found`.
2. `not public.project_can_edit(project_id)` → `access_denied`. Проверка
   явная: при `security invoker` UPDATE без права просто изменил бы ноль
   строк, и мастер не узнал бы об отказе.
3. `planned_date is not null` → `task_already_planned`; статус `completed`
   или `cancelled` → `task_closed`. Это не заявка панели.
4. `p_queue_id` не null и очереди с таким `id` в проекте заявки нет →
   `queue_not_found`.
5. Заблокировать контейнеры: `private.lock_board_container('queue', project_id,
   coalesce(queue_id::text, ''))` для исходной и целевой очереди, в
   отсортированном порядке ключей (одна блокировка, если очередь та же).
   Обе — чтобы параллельная перестановка исходной очереди не записала
   позицию заявке, которая уже ушла в другую; сортировка — от взаимной
   блокировки.
6. Если очередь меняется — `update tasks set queue_id = p_queue_id`
   (триггер §3.3 обнулит позицию).
7. Перенумеровать открытые заявки целевой очереди (`planned_date is null`,
   статус не `completed`/`cancelled`, `queue_id is not distinct from
   p_queue_id`) без перемещаемой в порядке §3.2, вставить её на
   `least(greatest(p_position, 0), count)`, обновить только строки, где
   позиция изменилась. Заявки с `null` получают позиции в том виде, в
   котором мастер их видел. Обновляется только `backlog_position`, поэтому
   триггер §3.3 позицию не сбрасывает.

В исходной очереди после переноса остаётся пропуск в нумерации — порядок
от этого не меняется, перенумеровывать её не нужно.

`revoke all ... from public, anon; grant execute ... to authenticated;`

`p_position` — место в списке целевой очереди **без** перемещаемой заявки,
как у `move_board_item`.

### 4.1 Гонки

- Перестановки и переносы, затрагивающие одну очередь, идут
  последовательно (advisory lock).
- Возврат с доски, планирование и смена очереди на странице заявки этот
  lock не берут. Худший случай: заявка, которую в ту же секунду
  запланировали, получит позицию, которая ничего не значит (панель
  фильтрует `planned_date is null`); при следующем возврате триггер её
  обнулит. Порядок остаётся однозначным за счёт `created_at, id`.

### 4.2 `updated_at`

Перестановка обновляет `updated_at` у заявок, чья позиция изменилась
(триггер `tasks_set_updated_at`). Сейчас `updated_at` заявок нигде в
интерфейсе не показывается. Если понадобится «недавно изменённые заявки»,
позицию нужно будет исключить из этого триггера.

## 6. Доска — `board/page.tsx` и `board/week-board.tsx`

- **Данные.** Страница загружает очереди проекта и заявки панелей (с
  `queue_id`) в порядке §3.2, группирует их по очереди. Заявкам в днях
  тоже нужен `queue_id` — чтобы знать, в какую панель они вернутся.
- **Панели.** В нижней сетке: «Текущие заявки», затем панели очередей, затем
  дополнительные списки. Панель очереди устроена как нынешняя
  `BacklogPanel`: заголовок — имя очереди, форма быстрого создания (заявка
  создаётся в этой очереди), список заявок.
- **Контейнеры dnd.** Вместо одного `BACKLOG` — по контейнеру на очередь:
  `queue:main` и `queue:<uuid>`. Id строк — `<контейнер>|<taskId>`.
- **Перетаскивание:**
  - внутри панели — сортировка (`SortableContext`, `verticalListSortingStrategy`;
    `DraggableTaskRow` переходит на `useSortable`), оптимистичный ход и
    `moveBacklogTaskAction`;
  - между панелями очередей — перенос в целевую очередь на место под
    курсором (или в конец, если курсор над самой панелью), тем же действием;
  - из панели в день — без изменений;
  - из дня в панель — только в панель **своей** очереди (остальные не
    подсвечиваются): `returnTaskToBacklogAction`, заявка встаёт наверх.
    Перенести в другую очередь можно уже из панели;
  - если индекс и очередь не изменились — ничего не делаем.
- Оптимистичное состояние откатывается при ошибке, toast с понятным
  текстом — как у остальных ходов.
- «Только просмотр»: без перетаскивания и без форм создания, как сейчас.

## 7. Страница заявки и страница «Заявки»

- **Страница заявки:** поле «Очередь» (select: «Текущие заявки» и очереди
  проекта) рядом с категорией. Показывается, только если в проекте есть хотя
  бы одна дополнительная очередь. Смена — `updateTaskQueueAction`; заявка
  встаёт наверх новой очереди. У «Только просмотр» — только текст.
- **Форма создания на странице «Заявки»:** то же поле «Очередь» при наличии
  дополнительных очередей, по умолчанию «Текущие заявки».

## 11. Отклонённые варианты

- **Отдельная таблица порядка** — не трогает `updated_at`, но добавляет
  таблицу со своими RLS-политиками, соединение в запросе и риск
  рассинхрона с `tasks`.
- **Дробный ранг без перенумерации** — меньше записей, но второй способ
  упорядочивания рядом с уже принятым в днях и списках; для десятков строк
  выигрыш не нужен.
- **Очередь как разновидность `board_lists`** — сэкономила бы экран
  настроек, но смешала бы пункты и заявки в одной таблице и потребовала бы
  защитных триггеров от «заявки в списке пунктов» и наоборот.
- **Строка основной очереди в `task_queues`** — единообразнее, но нужен
  перенос существующих заявок, создание строки для новых проектов и защита
  от удаления. `null` даёт то же без этого.
- **Очередь по исполнителю или категории** — исполнителя обычно назначают
  при планировании, а категория означает цех-заказчик.

## 12. Вне объёма (в roadmap)

- Метка очереди на карточках в днях недели.
- Фильтр по очереди на странице «Заявки».
- Ручной порядок панелей очередей.
- Сохранение места, куда бросили заявку при возврате с доски, — по решению
  пользователя она встаёт наверх своей очереди.
- Личный порядок для каждого участника.

## 13. Этапы реализации

1. Ручной порядок в основной очереди: колонка `backlog_position`, триггер,
   RPC, сортируемая панель. Проверяемо само по себе.
2. Очереди: `task_queues`, `queue_id`, перенос между панелями, настройки,
   поле на странице заявки.

Миграция одна (`0018`): на prod она уходит одним шагом после обоих этапов.
