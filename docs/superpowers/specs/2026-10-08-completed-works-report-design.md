# Отчёт «Выполненные работы за месяц» — дизайн

Дата: 2026-10-08. Статус: на согласовании. Roadmap «После MVP», п. 17.

## 1. Цель

Раз в месяц мастер отчитывается начальству: что ремонтный цех сделал для
каждого цеха-заказчика, кто делал и какие материалы ушли. Сейчас для этого
есть только архив заявок (фильтры, без выгрузки) и отчёт по расходу материалов
(без списка работ).

## 2. Решения, принятые с пользователем

| Вопрос | Решение |
|---|---|
| Назначение | Отчёт начальству, сгруппированный по цехам-заказчикам. |
| Строка заявки | Дата выполнения, название, исполнители, потраченные материалы. Описание — нет. |
| Период | Календарный месяц в timezone проекта, навигация ← →, как в отчёте по расходу. |
| Какие заявки | Только выполненные (`status = 'completed'`), по `completed_at`. Отменённые — нет. |
| Фильтр | По цеху, как в отчёте по расходу (включая архивные и «Без цеха»). |
| Выгрузка | CSV для Excel, совпадает с экраном, включая фильтр. |
| Доступ | Любой участник проекта, включая `viewer`, видит и выгружает (как отчёт по расходу, PRD §5). |
| Реализация | Новая SQL-функция `completed_works_report` (вариант 1). Переиспользование `search_archive_tasks` и вложенный запрос supabase-js отклонены (§8). |

## 3. Страница

`/[projectId]/reports` получает две вкладки (оформление — как вкладки
«Открытые / Архив» на странице «Заявки»):

* «Расход материалов» — текущий отчёт, без изменений; по умолчанию.
* «Выполненные работы» — `?report=works`.

Параметры адреса вкладки работ: `report=works`, `month=YYYY-MM`, `category`
(`all` по умолчанию, `none` — «Без цеха», id цеха). Разбор — существующими
`resolveMonth` и `resolveCategoryFilter`; неверные значения молча
сбрасываются. Навигация по месяцам и фильтр цеха — те же элементы, что у
отчёта по расходу; ссылки сохраняют `report=works`.

Заголовок карточки — «Выполненные работы по цехам», подпись: «Заявки,
выполненные в этом месяце. Цех — текущая категория заявки. Материалы — итог
расхода по заявке; если расход правили в другом месяце, он может не совпасть с
отчётом по расходу» (§3.2).

### 3.1 Содержимое

* Группа на цех. Порядок групп — `categories.sort_order`, затем название;
  «Без цеха» — последней. Заголовок группы: «Механический · 12» (число работ).
* Строка: дата выполнения (`дд.мм`), название — ссылка на заявку, ниже
  мелким — исполнители через «, » и материалы «Электрод 2 кг; Краска 1 л».
  Нет исполнителей / материалов — соответствующая часть не выводится.
* Внутри группы — по `completed_at` по возрастанию, затем `id`.
* Пусто: «За октябрь 2026 выполненных работ нет.»
* Ошибка загрузки: «Не удалось построить отчёт. Обновите страницу.»
* Кнопка «Скачать CSV» — только если есть строки.

### 3.2 Материалы

Количество — текущее `task_materials.quantity`, то есть итог расхода по
заявке. Отчёт по расходу относит расход к месяцу записи в журнале движений,
поэтому при правке расхода в другом месяце цифры двух отчётов могут
расходиться — это фиксируется в подписи страницы и в документации.
Порядок материалов в строке — по названию.

## 4. База данных — миграция 0025

`public.completed_works_report(p_project_id uuid, p_month date)`:

```text
returns table (
  task_id uuid,
  title text,
  completed_at timestamptz,
  category_id uuid,          -- null — без цеха
  category_name text,
  category_sort_order int,
  executor_names text[],     -- по имени
  materials jsonb            -- [{name, unit, quantity}] по названию; [] если нет
)
```

* `language sql stable`, `set search_path = ''`, **security invoker**: RLS
  `tasks`, `categories`, `task_executors`, `executors`, `task_materials`,
  `materials` действует. Нет доступа к проекту — нет строки `projects`,
  границ месяца нет, результат пуст (как `material_consumption_by_category`).
* Границы: `date_trunc('month', p_month)::timestamp at time zone p.timezone`
  и `+ interval '1 month'`, полуинтервал `[from, to)`.
* Только `t.status = 'completed'`, `t.project_id = p_project_id`.
* Порядок: `category_sort_order nulls last, category_name nulls last,
  completed_at, task_id`.
* `revoke all … from public, anon; grant execute … to authenticated`.
* Новых таблиц и политик нет. Выкладка безопасна в любом порядке.

Индекс: выборка по `(project_id, status)` и диапазону `completed_at`.
Существующих индексов достаточно для объёмов MVP (сотни заявок в месяц);
отдельный индекс не добавляется (CLAUDE.md §33).

## 5. Код

* `lib/business/works-report.ts` — чистые функции:
  * `groupWorksByCategory(rows)` → группы `{categoryId, categoryName, works[]}`
    в порядке строк RPC, «Без цеха» — `NO_CATEGORY_LABEL`;
  * `filterWorkGroups(groups, category)` — как `filterGroups` отчёта по расходу;
  * `formatMaterials(materials)` → «Электрод 2 кг; Краска 1 л»
    (`formatQuantity`);
  * `buildWorksCsv(groups, timezone)` — колонки «Цех; Дата выполнения;
    Заявка; Исполнители; Материалы»; дата `дд.мм.гггг` в timezone проекта.
* CSV-хелперы (`csvCell`, защита от формул, BOM, разделитель, десятичная
  запятая) выносятся из `material-report.ts` в `lib/business/csv.ts` и
  используются обоими отчётами; поведение отчёта по расходу не меняется
  (его тесты остаются зелёными).
* `app/(app)/[projectId]/reports/works-data.ts` — `loadWorksReport(projectId,
  monthParam, category)` для страницы и выгрузки (как `data.ts`).
* `app/(app)/[projectId]/reports/works/export/route.ts` — GET, проверка
  `projectId`, ответ `text/csv`, имя `completed-works-YYYY-MM.csv`,
  `Cache-Control: private, no-store`; ошибка — 500 с понятным текстом.
* `page.tsx` — вкладки; содержимое отчёта работ — отдельный серверный
  компонент `works-report.tsx`. Новых клиентских компонентов нет: фильтр
  цеха — существующий клиентский `CategoryFilter`, он получает
  необязательный `report` и сохраняет его в адресе при смене цеха.
* Ячейка «Материалы» в CSV — та же строка, что на экране; внутри неё «; »,
  поэтому ячейка берётся в кавычки (`csvCell`).

## 6. Ошибки и безопасность

* Технические ошибки RPC — в `console.error`, пользователю — общий текст (§31).
* Чужой проект: RLS → пустой отчёт и пустой CSV-ответ с заголовком (не 500).
* Неавторизованный запрос до route не доходит (`proxy.ts`).
* CSV: значения от пользователя (названия заявок, цехов, материалов, имена)
  экранируются и защищены от формул (`=`, `+`, `-`, `@`).

## 7. Тесты

pgTAP `completed-works-report.test.sql`:

* функция существует, `anon` без права выполнения;
* границы месяца в timezone проекта (23:30 МСК последнего дня — в месяце,
  00:30 МСК первого числа следующего — нет);
* отменённые и открытые не попадают;
* исполнители по имени, пустой массив без исполнителей;
* материалы `jsonb` с количеством, `[]` без материалов;
* порядок: по `sort_order` цеха, «Без цеха» последним, внутри — по дате;
* чужой проект — пусто; viewer видит.

vitest `works-report.test.ts`: группировка и порядок, фильтр по цеху и
«Без цеха», `formatMaterials`, CSV (BOM, заголовок, экранирование «;» и
кавычек, защита от формул, дата в timezone). Тесты CSV отчёта по расходу —
без изменений.

Браузер: 1280 и 375 — вкладки, навигация месяцев, фильтр, ссылки на заявки,
скачивание CSV, пустой месяц, консоль без ошибок.

## 8. Отклонённые варианты

* **`search_archive_tasks` с периодом** — лимит 1001 строка, нет материалов
  (второй запрос), фильтр по статусу и тексту не нужен.
* **Вложенный запрос supabase-js без миграции** — границы месяца в timezone
  проекта пришлось бы считать в TypeScript; ошибка на смене суток
  незаметна и критична для отчёта (CLAUDE.md §32).
