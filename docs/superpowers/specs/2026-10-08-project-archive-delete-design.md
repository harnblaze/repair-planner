# Архив и удаление проектов — дизайн

Дата: 2026-10-08. Статус: на согласовании. Roadmap «После MVP», п. 11; открытый
вопрос «Удаление проекта с расходом материалов падает».

## 1. Проблема

* В интерфейсе нельзя убрать ненужный проект: колонка `projects.archived_at`
  (0002) есть и учитывается списком проектов и layout проекта, но выставить её
  негде.
* Настоящее удаление проекта (сейчас — только прямым запросом владельца к API)
  падает, если в проекте был расход материалов: каскад удаляет `task_materials`,
  триггер `apply_task_material_change` пишет движение в `material_movements`
  уже удалённого проекта → нарушение FK `material_movements_project_id_fkey`
  (воспроизведено локально).
* Файлы фото проекта в Storage каскад не удаляет; после удаления строки проекта
  их никто не сможет удалить (RLS `storage.objects` проверяет права через проект).

## 2. Решения, принятые с пользователем

| Вопрос | Решение |
|---|---|
| Модель | Архив + удаление навсегда из архива. |
| Кто | Только владелец проекта (`project_access = 'owner'`). |
| Видимость архива | Проект в архиве скрыт у всех; список «Архив» видит только владелец. |
| Подтверждение удаления | Ввод названия проекта. |
| Защита в БД | Удалить можно только проект в архиве (политика DELETE). |

## 3. Поведение и интерфейс

* **Отправить в архив** — карточка «Архив» в настройках проекта, только у
  владельца: пояснение («Проект пропадёт у всех участников, данные сохранятся,
  его можно вернуть») и кнопка «Отправить в архив» с `window.confirm`. После
  успеха — переход на `/projects`.
* **Список проектов** (`/projects`) — под активными проектами свёрнутый раздел
  «Архив (N)» (`<details>`), только проекты, где пользователь — владелец.
  У каждого: «Вернуть» и «Удалить навсегда».
* **Удалить навсегда** — раскрывающаяся под проектом форма (без модального окна:
  в проекте нет компонента диалога, новая зависимость не нужна): «Будут удалены
  все заявки, материалы, списки и фото проекта. Это необратимо. Введите название
  проекта:», поле ввода, кнопка «Удалить навсегда» (активна при совпадении
  названия). Сравнение — после `trim`, с учётом регистра.
* Участники и наблюдатели архивный проект не видят: он не попадает в список,
  прямая ссылка — 404 (уже реализовано фильтром `archived_at is null`).
  Принять приглашение в архивный проект нельзя (уже реализовано в 0012).

## 4. База данных — миграция 0027

1. **Триггер `public.apply_task_material_change`** — в начале функции:
   при `tg_op = 'DELETE'` и отсутствии строки `public.projects` с
   `id = old.project_id` — `return old` без изменения остатка и движения.
   Удаление расхода в живом проекте работает как прежде.
2. **Политика `projects_delete`** — `using (public.project_access(id) = 'owner'
   and archived_at is not null)`.
3. **RPC `public.project_attachment_paths(p_project_id uuid, p_limit int default 1000)
   returns setof text`** — имена объектов `storage.objects` с
   `bucket_id = 'task-attachments'` и `name like p_project_id::text || '/%'`;
   только если `project_access(p_project_id) = 'owner'` и проект в архиве,
   иначе пусто; порядок `name`; `limit least(greatest(coalesce(p_limit, 1), 1), 1000)`;
   `language sql stable`, `set search_path = ''`, security invoker;
   `revoke all … from public, anon; grant execute … to authenticated`.

Новых таблиц нет, данные миграция не меняет. Применять до выкладки кода: без
RPC удаление навсегда остановится с общим сообщением об ошибке (проект не
тронут), архив и возврат работают и без миграции.

## 5. Код

Server actions в `app/(app)/projects/actions.ts` (рядом со списком проектов) —
все с проверкой входа (uuid, Zod) на сервере:

* `archiveProjectAction(projectId)` — `update projects set archived_at = now()
  where id = … and archived_at is null` с `.select("id")`; 0 строк — «Отправить
  в архив может только владелец проекта.»; успех — `revalidatePath("/projects")`
  и `redirect("/projects")`.
* `restoreProjectAction(projectId)` — `archived_at = null where archived_at is
  not null`; 0 строк — то же сообщение о правах; успех — `revalidatePath`.
* `deleteProjectAction(projectId, confirmName)`:
  1. читает проект (`name`, `archived_at`) под RLS; нет строки или не в
     архиве — «Удалить можно только проект в архиве.»; `confirmName.trim()` ≠
     `name` — «Название не совпадает.»;
  2. удаляет файлы пачками: `project_attachment_paths` → если пусто, дальше;
     иначе `storage.from(ATTACHMENTS_BUCKET).remove(paths)`; ошибка или удалено
     меньше, чем запрошено, — стоп, «Не удалось удалить проект. Попробуйте ещё
     раз.», проект не удаляется; не более 100 пачек (защита от бесконечного
     цикла);
  3. `delete from projects where id = …` с `.select("id")`; 0 строк — сообщение
     о правах; ошибка — общее сообщение;
  4. `revalidatePath("/projects")`.

UI: `app/(app)/[projectId]/settings/archive-project-section.tsx` (client),
`app/(app)/projects/archived-projects.tsx` (client, раздел архива с формой
удаления). Тексты ошибок — `PROJECT_MESSAGES` в `lib/errors.ts`.

## 6. Порядок удаления и сбои

Сначала файлы, потом строка проекта: после удаления проекта RLS не даст удалить
файлы. Сбой между шагами 2 и 3 оставляет проект в архиве без части фото —
повторное «Удалить навсегда» завершает удаление. Сбой Storage на шаге 2 — проект
не тронут. Технические детали — только в `console.error`.

## 7. Безопасность

* Все три действия опираются на RLS: архив/возврат/удаление — политики
  `projects_update`/`projects_delete` (владелец); файлы — `task_attachments_objects_delete`.
* RPC путей отдаёт данные только владельцу архивного проекта.
* Удаление активного проекта невозможно и прямым запросом к API.
* Service role не используется.

## 8. Тесты

* pgTAP `project-archive-delete.test.sql`: владелец не может удалить активный
  проект, может — архивный; member не может удалить архивный; удаление проекта с
  расходом проходит, движений не добавляется; удаление расхода в живом проекте
  пишет движение `adjustment`; RPC путей — пусто для активного проекта, для
  member, для чужого проекта; для владельца архивного — только его файлы bucket
  `task-attachments`.
* vitest `projects/actions.test.ts`: архив/возврат (успех, 0 строк);
  удаление — неверное название, не в архиве, несколько пачек файлов, ошибка
  Storage и неполное удаление (проект не удаляется), успех.
* Браузер: в архив → проект пропал, есть в «Архиве» → вернуть → в архив →
  удалить проект с фото и расходом → в БД и Storage ничего не осталось,
  консоль без ошибок.

## 9. Отклонённые варианты

* **Сначала БД, потом файлы** — невозможно: RLS Storage проверяет права через
  удалённый проект.
* **Edge Function / service role** — противоречит CLAUDE.md §11.
* **Оставлять файлы «сиротами»** — без проекта их никто не удалит.
* **Режим «только чтение» для архивного проекта в БД** — UI доступа не даёт;
  лишняя сложность во всех политиках.
* **Модальное окно** — нет компонента диалога; раскрывающаяся форма не требует
  зависимости.
