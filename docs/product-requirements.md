# Product Requirements

> Статус: согласовано 2026-09-11. Документ описывает MVP приложения для планирования работ ремонтно-строительного цеха.

## 1. Пользователь и задача

Единственный пользователь MVP — **мастер ремонтно-строительного цеха**. Все пользователи имеют одну роль.

Мастер должен, открыв приложение утром, за несколько секунд понять:

* что нужно сделать сегодня;
* кто это делает;
* какие материалы были потрачены;
* чего не хватает на остатке.

## 2. Основной процесс

```
Заявка от другого цеха
        ↓
Текущие заявки (backlog)
        ↓
Мастер выбирает рабочий день
        ↓
Назначает исполнителей
        ↓
Указывает фактически использованные материалы
        ↓
Работа выполняется
        ↓
Статус «Выполнена»
```

Если работа не закончена — задача добавляется в следующий рабочий день и **остаётся видимой в предыдущих днях**, в которых над ней работали. Пятница переносится на понедельник.

### 3.2 Не входит в MVP

RBAC сверх owner/member; приглашения пользователей; совместное редактирование; Telegram / email / push; складской модуль; закупки; бухгалтерия; финансовые отчёты; производственный календарь и праздники; отпуска; автоматическое распределение загрузки; аналитика; мобильное приложение; офлайн-режим.

### 3.3 Предусмотрено архитектурно, но не реализуется

| Возможность | Что уже заложено |
|---|---|
| Приглашения в проект | Таблица `project_members`, роль в enum, все RLS построены на членстве |
| Уровни доступа (viewer) | `project_role` расширяется через `ALTER TYPE ADD VALUE` |
| Месячные отчёты по расходу | Append-only журнал `material_movements` с привязкой к задаче и дате |

| Пользовательские списки | Универсальная модель `board_lists` / `board_items` |

## 4. Согласованные бизнес-правила

### 4.1 Рабочие дни

Рабочие дни MVP — понедельник–пятница. Суббота и воскресенье — выходные. Праздники не учитываются.

«Следующий рабочий день» вычисляется **единственной** функцией `lib/business/working-days.ts`; дублирование этой логики в компонентах запрещено.

### 4.2 Timezone

У проекта есть поле `timezone`, значение по умолчанию — `Europe/Moscow`.

Плановые даты хранятся типом `date` (без времени), поэтому timezone влияет только на вычисление «какой сегодня день» и на подсветку текущего дня на доске. Часовой пояс браузера не используется никогда.

### 4.3 Планирование и перенос

* Задача может быть запланирована на **несколько рабочих дней**.
* Перенос незавершённой задачи **добавляет** новый день и **сохраняет** предыдущие: на доске видно, что работа шла вторник → среда → четверг.
* Перенос **не создаёт** новую задачу — идентичность исходной задачи сохраняется.
* День расписания помечается признаком `carried_over`, что отличает перенос от первичного планирования.
* В прошедших днях незавершённая задача отображается приглушённо с пометкой «перенесена на …» (дата — реальный следующий день работы).

### 4.4 Drag-and-drop на доске

Решения согласованы 2026-09-13.

| Перетаскивание | Правило |
|---|---|
| «Текущие заявки» → день | Задача планируется на день в указанное место; статус `new` → `planned`. Отложенную задачу нельзя поставить раньше последнего дня её истории. |
| Порядок внутри дня | Для любой карточки, включая приглушённые дни истории. |
| День → другой день недели | Только для задачи с единственным днём расписания; статус не важен (в т.ч. завершённые). Задачи, которые переносились или откладывались, между днями не перетаскиваются — дату можно изменить в карточке. |
| День → «Текущие заявки» | Только текущий (не исторический) день незавершённой задачи. См. «Отложить» ниже. |
| Порядок в дополнительных списках | Внутри одного списка. Перенос записи между списками не реализован. |
| Порядок в «Текущих заявках» | Не поддерживается: панель упорядочена по дате создания. |

**Отложить (вернуть в «Текущие заявки»).** Задача не копируется. Если работа не начиналась (статус `new`/`planned`), все дни — только план и удаляются. Если задача `in_progress`/`paused`, дни до сегодняшнего включительно (в timezone проекта) остаются историей, последний помечается «Отложена», будущие дни удаляются. При повторном планировании добавляется новый день, история сохраняется, на историческом дне пишется «Отложена, продолжена …». Завершённую или отменённую задачу вернуть нельзя.

Статус при возврате в «Текущие заявки» не меняется. Поле даты в карточке задачи для задачи из «Текущих заявок» (в т.ч. отложенной) планирует её с сохранением истории; для уже запланированной задачи оно по-прежнему заменяет весь план.

Все действия дублируются без перетаскивания (карточка задачи); с клавиатуры перетаскивание начинается пробелом.

### 4.5 Материалы

* Расход списывается **сразу при добавлении строки материала в задачу**, а не при завершении задачи.
* Правка количества корректирует остаток на дельту; удаление строки возвращает материал на остаток.
* Списание больше остатка **разрешено**, но UI показывает явное предупреждение. Отрицательный остаток — сигнал «учёт отстал от факта», исправляется приходом или корректировкой.
* Если `current_balance <= minimum_balance` — в интерфейсе показывается предупреждение о низком остатке. Никаких внешних уведомлений.
* Изменение остатка и запись в журнал движений всегда происходят в одной транзакции на стороне PostgreSQL.

### 4.6 Статусы задач

В базе используются стабильные значения: `new`, `planned`, `in_progress`, `paused`, `completed`, `cancelled`. Русские названия — только на уровне представления; бизнес-логика на них не завязывается.

### 4.7 Проекты

Доступ строится по цепочке **User → Project → Project data**. Данные разных проектов полностью изолированы. Создатель проекта автоматически становится его владельцем через запись в `project_members`.

### 4.8 Удаление справочников

Категории, исполнители и материалы, на которые есть исторические ссылки, **архивируются** (`is_active` / `is_archived`), а не удаляются, чтобы не разрушать историю задач и движений.

## 5. Обработка ошибок

Пользователю показываются понятные сообщения на русском языке. Технические детали (SQL, коды ошибок, идентификаторы, stack trace) попадают только в серверные логи.
