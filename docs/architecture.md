# Architecture

> Статус: согласовано 2026-09-11. Код ещё не написан — документ описывает целевую архитектуру MVP.

## 1. Стек

| Слой | Решение | Обоснование |
|---|---|---|
| Framework | Next.js 16, App Router | Требование проекта; Server Components снижают объём клиентского кода. Установлена актуальная стабильная версия (16.3.4) вместо ранее предполагавшейся 15 — на момент реализации это текущий latest |
| Язык | TypeScript (strict) | |
| UI | Tailwind CSS 4 + shadcn/ui | Компоненты копируются в репозиторий, нет тяжёлой зависимости |
| Backend | Supabase (PostgreSQL, Auth, Storage) | |
| SSR-интеграция | `@supabase/ssr` | Единственный поддерживаемый способ работы с cookie-сессией в App Router |
| Формы | React Hook Form + Zod | Одна Zod-схема используется и на клиенте, и в Server Action |
| Runtime | Node.js 22 | Установлен в окружении |

Drag-and-drop в MVP не реализуется, библиотека не добавляется (см. §7).

В Next.js 16 файл `middleware.ts` переименован в `proxy.ts` (функциональность та же, изменилось только имя файла и экспортируемой функции). Проект использует новое имя.

## 2. Границы ответственности

```
Browser (Client Components)
   │  формы, модальные окна, локальное состояние
   ▼
Server Components / Server Actions
   │  чтение данных, валидация Zod, вызов Supabase от имени пользователя
   ▼
PostgreSQL (Supabase)
   │  RLS, CHECK-ограничения, триггеры, SECURITY DEFINER функции
   ▼
   данные
```

Ключевой принцип: **безопасность и целостность обеспечиваются в PostgreSQL**, а не в приложении. Приложение отвечает за UX и удобные сообщения об ошибках. Даже при полностью скомпрометированном клиенте пользователь не получит доступ к чужому проекту.

## 3. Клиент и сервер

* По умолчанию — **Server Component**.
* Client Component создаётся только там, где нужна интерактивность: формы, диалоги, фильтры, локальное состояние.
* Данные читаются в Server Components через серверный Supabase-клиент.
* Мутации выполняются **Server Actions**, которые: валидируют вход через Zod → вызывают Supabase → вызывают `revalidatePath`.
* `service_role` ключ не используется нигде в приложении. Все операции идут от имени пользователя; повышенные права нужны только внутри `SECURITY DEFINER` функций в БД.

Три клиента Supabase:

| Файл | Назначение |
|---|---|
| `lib/supabase/client.ts` | браузерный клиент (только `anon` ключ) |
| `lib/supabase/server.ts` | серверный клиент для Server Components и Server Actions |
| `lib/supabase/proxy.ts` | обновление сессии, защита маршрутов; вызывается из `proxy.ts` |

## 4. Маршрутизация и выбор проекта

Активный проект — часть URL: `/(app)/[projectId]/...`. Это даёт:

* естественную изоляцию данных в запросах;
* работающие «назад»/«вперёд» и закладки на конкретный проект;
* отсутствие скрытого глобального состояния «текущий проект».

Layout `app/(app)/[projectId]/layout.tsx` один раз проверяет доступ к проекту и отдаёт контекст (название проекта, timezone, роль) вниз по дереву. Если доступа нет — `notFound()`, без различения «не существует» и «нет доступа».

## 5. Бизнес-логика

Вынесена в `lib/business/`, не размазана по компонентам:

| Модуль | Ответственность |
|---|---|
| `working-days.ts` | является ли день рабочим; следующий/предыдущий рабочий день; неделя доски |
| `task-planning.ts` | планирование задачи на день, перенос, снятие с дня |
| `materials.ts` | правила расхода, признак низкого остатка, форматирование количеств |
| `dates.ts` | преобразования `date` ↔ строка с учётом `project.timezone` |

Правила, которые обязаны жить в БД (а не только здесь): пересчёт остатка, запись журнала движений, кеш планового дня задачи.

## 6. Доска проекта

Доска — горизонтальный набор колонок:

```
[ Текущие заявки ] [ Пн 14.09 ] [ Вт 15.09 ] [ Ср 16.09 ] [ Чт 17.09 ] [ Пт 18.09 ] │ [ Материалы к заказу ] [ Напоминания ] [ Мероприятия ]
        задачи            задачи из task_schedule                                                   board_items
```

Источники данных различаются, а компонент колонки — **один**:

| Колонка | Источник |
|---|---|
| Текущие заявки | `tasks`, у которых нет записей в `task_schedule` и статус не `completed`/`cancelled` |
| Рабочий день | `task_schedule` за конкретную дату + связанные задачи |
| Дополнительные списки | `board_items` соответствующего `board_lists` |

«Текущие заявки» **не** являются записью в `board_lists`: это задачи со всей обвязкой (исполнители, материалы, категория), и попытка уложить их в универсальную модель заметок обеднила бы модель задач. Универсальная модель списков применяется там, где она действительно универсальна — к простым чек-листам, что сразу даёт возможность пользовательских списков в будущем.

Неделя доски вычисляется от «сегодня» в timezone проекта; предусмотрена навигация по неделям.

## 7. Почему в MVP нет drag-and-drop

Перенос и планирование закрываются быстрыми действиями в карточке задачи («Запланировать на…», «Перенести на следующий рабочий день»). Это меньше кода, лучше работает с клавиатуры и на узком экране. Поле `position` в `task_schedule` и `board_items` уже заложено, поэтому `@dnd-kit` можно добавить позже без изменения схемы БД.

## 8. Работа с ошибками

* Server Action возвращает дискриминированный результат `{ ok: true, data } | { ok: false, error: string }`, где `error` — сообщение для человека.
* Технические детали логируются на сервере.
* Коды ошибок PostgreSQL (уникальность, нарушение FK, нарушение RLS) маппятся в понятные фразы централизованно, в `lib/errors.ts`.

## 9. Производительность

* Запросы всегда ограничены проектом и, для доски, диапазоном дат недели.
* Доска загружается одним-двумя запросами с явным списком колонок, без `select *`.
* Индексы под каждый шаблон запроса описаны в `docs/database.md`.
* Пагинация применяется в архиве задач и в журнале движений материалов, не на доске.
* `revalidatePath` — основной механизм инвалидации; клиентский кеш-слой в MVP не вводится.

## 11. Тестирование и проверки

| Что | Чем |
|---|---|
| Бизнес-функции (рабочие дни, перенос, расчёт остатков) | Vitest, unit-тесты |
| Типы | `tsc --noEmit` |
| Стиль | ESLint (конфигурация Next.js) |
| RLS | отдельный скрипт/тест: пользователь A не видит и не меняет данные пользователя B |

Тесты RLS обязательны: это единственный слой, который нельзя проверить глазами.

## 12. Переменные окружения

```
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
```

`SUPABASE_SERVICE_ROLE_KEY` в приложении не используется; если он когда-либо понадобится для служебных скриптов — только в серверном окружении и никогда не в коде, попадающем в браузер. Файл `.env.local` в git не коммитится, в репозитории хранится `.env.example`.
