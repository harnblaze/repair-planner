## Открытые вопросы

Ни один из них не блокирует этапы 1–2.

| Вопрос | Когда нужен ответ |
|---|---|
| Должен ли перенос быть автоматическим (незавершённые задачи сами переезжают на следующий рабочий день) или только по действию мастера? Пока предполагается только ручной. | Этап 8 |
| Нужна ли задаче плановая трудоёмкость или срок от заказчика (дедлайн)? В MVP не закладывается. | После MVP |
| Нужно ли ограничивать список исполнителей, доступных для выбора, только активными? Пока да, с возможностью показать архивных. | Этап 6 |
| Как показывать задачу, запланированную на прошедшую неделю и незакрытую, — поднимать в текущую неделю или оставлять в прошлом? | Этап 7 |

## После MVP

Порядок ориентировочный, реализуется только по отдельному запросу.

1. Месячный отчёт по расходу материалов (данные уже есть в `material_movements`).
2. UI прихода и корректировки материалов.
3. Приглашение пользователей в проект, роль `viewer`.
4. Drag-and-drop на доске (`@dnd-kit`, поле `position` уже есть).
5. Праздники и производственный календарь (таблица `holidays`).
6. Пользовательские дополнительные списки.
7. Вложения к задачам (Supabase Storage).
8. Фильтры и поиск по задачам, архив выполненных работ.
9. Индивидуальные графики исполнителей, загрузка по дням.

## Отклонённые идеи

| Идея | Причина |
|---|---|
| Сущность «склад» | Прямо исключена требованиями; материалы принадлежат проекту |
| `planned_quantity` у материала в задаче | Учитывается только фактический расход |
| Чистый event sourcing для остатков | Избыточно для MVP, усложняет каждый запрос доски |
| Отдельная таблица `task_transfers` | `task_schedule` уже является историей переносов |
| «Текущие заявки» как запись в `board_lists` | Обеднило бы модель задач ради формальной универсальности |
| Drag-and-drop в MVP | Закрывается быстрыми действиями; библиотека добавляется позже без изменения схемы |
